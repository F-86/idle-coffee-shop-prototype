# 测试文档规范

## 范围与依据

最终产品规格决定测试范围；里程碑计划决定本轮执行范围。测试计划必须列出目标、纳入及排除项、版本、环境、用例与参数、完成标准、风险和汇报位置。

用例预期引用 `docs/product/` 中的需求 ID 和规则版本。当前代码只用于理解现状或定位操作。规格有歧义时记录待决策；不能读取实现公式后用同一公式证明实现正确。

## 目录与复用

- 按功能域/模块/场景分层，叶子文件是一条独立用例，例如 `cases/economy/upgrades/purchase/TC-ECO-001.md`。
- 用例 ID 为 `TC-域缩写-三位序号`，全库唯一且不随移动改变；需求 ID 为 `REQ-域缩写-三位序号`。
- 一个用例验证一个行为，可同时断言其 UI、数值和保存结果；可独立准备与清理，不依赖上一用例成功。
- 计划通过 ID 和文件链接引用，不复制正文。相同业务的边界值使用参数表，不把不同业务塞进一个巨大用例。
- 公共流程描述“如何准备”，fixture 描述“准备成什么状态”；UI 定位属于执行适配，不是业务规则。

## 用例必填内容

采用 [用例模板](templates/test-case.md)。包含 ID、标题、需求、优先级、类型、标签、规格状态、fixture、目标、前置条件、数据、步骤与逐步预期、超时、通过条件、证据、清理和待决策项。

数据明确单位、精度、边界值及随机种子（若使用）。等待写成“观察条件，最长 N 秒”，并区分产品要求的时限和测试运行预算；不可只写“等一会儿”。有未绑定变量的 draft 用例不得当作可执行用例。

## 状态分离

规格状态：draft（未定或不完整）、accepted（需求和断言明确，具备执行定义）、deprecated（保留历史，说明替代）。实现状态另记在覆盖矩阵，不能用规格状态表示开发进度。

| 执行结果 | 定义 |
| --- | --- |
| PASS | 实际执行且所有断言满足，有必要证据 |
| FAIL | 明确违反已确认规则，包括本阶段必需功能未实现 |
| BLOCKED | 环境、工具、数据或规则不明确，无法完成判断 |
| NOT_RUN | 计划中但尚未执行，必须写原因 |
| FLAKY | 同版本同条件重试结果不一致，原因未解释 |

计划外项为 out-of-scope，不算执行结果。代码在场不等于已验证。重复尝试逐次记录；重试通过不能抹掉首次失败。

## 优先级与完成标准

用例优先级：P0 核心经营与资产正确性；P1 主要成长和恢复；P2 次要功能及兼容；P3 低影响细节。

本轮报告完成：所有计划内用例/参数/环境都有结果或明确未执行原因，失败和阻塞有证据或证据缺失说明，给出覆盖缺口及后续动作。计划执行完成：无 NOT_RUN 且全部有执行结论；BLOCKED 必须明确披露。两者均不等于版本验收通过。

默认版本验收门槛：全部必选实例 PASS；没有未解决的 S0/S1 缺陷；必选项无 BLOCKED/FLAKY/NOT_RUN；需求覆盖无未说明缺口。例外必须在报告记录影响与明确接受来源，不以笼统“95%通过率”替代。

统计以“用例 × 参数 × 环境”为实例；报告总数及各状态计数，PASS/计划实例总数为通过率，计划外项单列。

## 问题汇报

采用 [缺陷模板](templates/bug-report.md)，包含预期依据、实际结果、最短复现、版本、初始状态、频率、证据、影响、可恢复性。将观察事实与疑似原因分开；不强行给出根因。

严重度与用例优先级分开：S0 无法经营/大范围资产丢失；S1 主要流程失效/收益或持久化严重错误；S2 局部异常且可绕过；S3 轻微视觉或文案。按实际影响评定，不单凭功能名称。

产品缺陷、未实现需求、环境故障、工具定位问题、测试数据问题、规格缺口分别标注。重复问题链接同一缺陷，保留各次发生证据。每轮使用 [运行报告模板](templates/test-run.md)，汇报范围、结论、重要问题、限制和下一步。
