# 真实浏览器帧节奏测量计划

2026-10-04。辅助 REQ-3D-024；独立用例 TC-3D-015。目的是量化指定 Mac 当前版本的卡顿线索；不借 FPS 宣称温度、功耗、GPU耗时或实际屏幕呈现帧数。

## 仪表定义与边界

- 仅严格 `?qa=1` 创建 Performance QA。默认折叠，不采样、不查场景、不更新文本；展开后使用原应用 RAF 链，在实际调用场景 update/render 返回后记录该次 RAF 的浏览器单调时间戳。不是模拟时钟，也不是字面上的 scene.render 开始/结束时间。仍可能受浏览器调度、CPU/GPU阻塞和诊断自身工作影响。
- FPS 是相邻渲染提交的间隔数量÷完整间隔总秒数。p50/p95 为最近10秒内结束的完整间隔的 nearest-rank 分位数；一个超过10秒的前台长间隔仍完整计入，故覆盖时长可能超过10秒。起始首帧只建立参照，不当作零时长帧。
- 长间隔分别严格 `>50ms`、`>100ms`；这是帧提交节奏，不是 Long Tasks API。正常省电30fps约33.3ms不算50ms长间隔，高刷新屏的一次掉帧仍可能小于50ms，因此同时看p95/max。
- 两个4096长度 Float64Array，64KiB固定样本内存；1Hz读取/排序/场景汇总与DOM更新，每帧只记录标量。超过容量且被覆盖的间隔仍属于窗口时明确显示容量截断；本段计数/累计间隔时间与长间隔总数仍保留。没有网络、后台采样任务、额外RAF或存档字段。
- 只在页面 visible 且 document.hasFocus() 时采样；隐藏/焦点丢失/恢复、模式切换、尺寸变化、读档/新店、WebGL上下文丢失/恢复都重开段。已有scene对象不等于可用WebGL；上下文丢失不报告有效FPS。GPU完成和像素呈现仍需专用工具。
- 冻结保留最近一次1Hz显示及对应上下文，最多比点击早约1秒；多次点击不重复拼接。重新开始清除统计，不触碰游戏状态。生命周期/模式/尺寸变化会使冻结失效并重开段，旧截图应先保存。
- 收起 Route QA 停止其逐帧投影、marker、快照和DOM处理；核心事件仍保留有限历史，展开时刷新。测量包含性能面板本身与少量QA事件观察成本，不能直接称为无仪表开销的正常玩家帧率。

## Mac执行条件

1. 使用同一台已授权Mac、同一浏览器/版本、同一显示器及刷新设置；记录机型、OS、浏览器、可确认的显示刷新率、供电/低电量模式和大负载应用情况。不能推测未暴露的GPU或温度。测试期间不擅改系统/电源设置。
2. 构建并确认精确任务提交/资源。用独立本地测试origin或独立浏览器存储，禁止覆盖用户日常Pages存档。`?qa=1`本身不会隔离保存。当前任务分支不会触发main-only Pages；实测新版前由负责人选择既有授权本地预览或审查后的现有发布流程，不另设发布目标。
3. 固定1280×900 CSS viewport、100%页面缩放、同一相机pan/锚点；从面板记录实际viewport、设备DPR和buffer，实际不能达到该viewport时记录真实值并固定，不能把截图物理像素当CSS尺寸。
4. 主场景仅正常自动客流，A/B及经理同等级/配方，不招客、不升级、不改配方，经营弹窗关闭。记录每段开始/结束的core elapsed、客人数/阶段、等级/配方、mesh数。若使用现有测试存档，记录来源、路线版本和客流，不假称与新店同负载。
5. 页面处于前台且有焦点，关闭 Route QA，仅展开 Performance QA。不用截图截图间隔估算FPS，不注入脚本改时间，不用NullEngine数据替代真机结果。

## 有界采样步骤

- 每个模式（smooth、balanced、low-power）等待至少30真实秒预热，然后点击“重新开始计时”。以面板“本段”时间达到至少60秒为结束条件，在约15/30/60秒保留可读读数或截图；最后冻结、保存读数。单段需无隐藏/焦点/resize/模式重开；有重开则把被打断段标为无效并重做该段，不拼接。
- 按 smooth→balanced→low-power→smooth 重复，共四个60秒有效段（加各段预热约6分钟）。最后smooth用于观察顺序/状态/设备热身变化，不能据此独立归因于温度。模式切换后关闭设置窗口并再次确认pan/尺寸。
- 顺序自然经营会改变客流和elapsed，因此此轮是同设备筛查，不是严格相同负载的因果A/B。若差异明显，后续用同一个隔离测试档、同一起始状态、同样预热时刻分别重跑；不得为追求可比性改写用户日常档。
- 另做一次可见→切后台20真实秒→返回：隐藏期间RAF停止；返回首帧重新计时、无20秒长间隔。再验证一次可见但失焦：读数PAUSED，恢复后新段。它们是生命周期检查，单独记结果，不混入四个前台段。
- 截图/浏览器工具可能打断焦点或造成CPU压力，记录这种干扰；主段尽量不操作页面，若工具导致重开，使用更少的被动读取或结束时一次读取并如实说明证据粒度。

## 记录和判读

逐段写：精确commit/资源、真实开始结束时刻、模式、窗口CSS/设备DPR/buffer/有效DPR、前台/焦点、场景等级/配方/客流/mesh上下文、累计秒数/间隔/FPS/长间隔总数，以及最后10秒p50/p95/max/长间隔。分列 PASS（有效完成采样）、FAIL（发现明确问题）、BLOCKED（工具/浏览器条件）和NOT_RUN。

期望预算：smooth随显示RAF；balanced最高60fps；low-power最高30fps。这是上限而非保证。1280×900@2的理论buffer分别2560×1800、1920×1350、1280×900；必须对照实际显示的buffer，不能用理论值当实测。持续p95明显高于该模式正常间隔或反复>50/100ms，才有具体调度/绘制卡顿线索；还不能定位GPU或证明优化收益。

若授权Mac工具能提供进程CPU、Energy Impact或设备温度，可在同条件下单独记录工具名、单位、真实时间和持续窗口。Energy Impact不是摄氏度；CPU占用也不是GPU功耗。无温度传感读数则温度NOT_RUN。短时帧率正常也不能排除持续运行发热。
